# Политика выбора игрока для демонстрации

Оба player-ноутбука выбирают демонстрационного игрока **программно, по явному
воспроизводимому правилу**, а не вручную. Правило разное в двух ноутбуках —
намеренно, т.к. они показывают два разных сценария, а не один и тот же кейс.

## `player_utility_analysis.ipynb` — best-case сценарий

**Правило:** среди игроков с ≥8 матчей в датасете — взять того, у кого больше всего бросков.

**Зачем так:** 82,295 из 89,052 трейсеров встречаются только в одном матче — на
одном матче почти любая метрика по типу гранаты (флеш/HE/молотов) статистически
бессмысленна (N < MIN_N). Этот ноутбук — демонстрация метода на **максимально
доступной для этого датасета** выборке одного игрока (9 матчей, 310 бросков),
чтобы показать, какие выводы в принципе возможны, когда данных достаточно.

## `player_rating_bin_report.ipynb` — typical-case сценарий

**Правило:** среди игроков с ≥2 матчей — взять игрока на медиане по числу матчей
и по числу бросков (с детерминированным tie-break: больше матчей с известным
рейтингом → меньший `player_id`).

**Зачем так:** 79% игроков с ≥2 матчами имеют ровно 2 матча — медиана этой группы
и есть реалистичный профиль обычного пользователя в данных такого формата.
Этот ноутбук — честная демонстрация того, что получит **типичный** клиент, а не
лучший случай.

## Итог

Разные критерии — это и есть единая политика: **каждый ноутбук явно документирует
свой критерий отбора и обоснование числами**, вместо произвольного "взяли
интересного игрока". При портировании в продукт правило становится тривиальным —
игрок не выбирается, а приходит от клиента; эта политика актуальна только для
демонстрационных POC-ноутбуков на данном датасете.
